# Technical writing

Produce documentation that a tired engineer can use correctly on the first read.

Choose the document's job before writing:

- tutorial for guided learning through a working result;
- how-to for completing a real task;
- reference for accurate lookup;
- explanation for understanding a bounded design or tradeoff.

Do not force one file to serve incompatible jobs. A short embedded reference or example is fine when it directly supports the document's main job.

Preserve the requested facts, structure, genre, and level of detail. Verify symbols, paths, commands, counts, and behavior against the repository. Do not invent roadmap status, compatibility, performance claims, or examples that look executable but are not.

For a substantial document or review, read [references/style-guide.md](references/style-guide.md). For a short edit, apply only the relevant rules.

Use `unslop` for the final prose pass when the document needs one. Return the document or concrete review findings, not a report about the writing process.
