Forge architecture plan · 4 September 2026

Migrate Forge to dendritic without changing what the machines do.

Keep flake-parts and flake-file, replace class-specific registries and host-owned imports with typed, feature-owned aspects, then swap the loader only after every loaded Nix file has one meaning. Preserve all five user-facing configurations and every deployment gate throughout.

Recommended direction

Adopt the pattern, not another framework.

Forge is already built on flake-parts, auto-loads its top-level parts, and distributes flake inputs through flake-file. That means the useful half of the foundation is present. The migration should focus on the semantic inversion: a file owns an aspect across module classes, while a host merely selects aspects.

Add flake-parts' class-checked flake.modules.<class>.<aspect> option, keep flake-file, and initially keep the current loader. Once all ordinary .nix files are flake-parts modules and helper files are explicitly excluded, replace flake-parts-builder with denful/import-tree and delete the bootstrap/template scaffolding it made necessary.

Success condition

Adding or removing a feature means changing its aspect and a host's short selection list; it does not require editing a registry, threading a new special argument, or knowing which kind of module a path contains.

Baseline prerequisite

Atlas does not currently evaluate in this worktree environment because the locked shop-empty-track GitHub archive returns 404. Record or repair that baseline before using “all hosts green” as a migration gate.

Architecture decisions

Three choices keep the migration bounded.

Module model

Use flake.modules

Import inputs.flake-parts.flakeModules.modules once. Publish aspects under nixos, darwin, and homeManager; gain class checking and remove the custom flake.homeModules option.

Input ownership

Keep flake-file

Move each input declaration next to the aspect that consumes it. Retain generated flake.nix and the write-flake gate. Dendritic does not require a handwritten flake manifest.

Tree loader

Switch loaders last

The current loader is adequate for the transition. Use import-tree only after a file-semantics audit, then remove flake-parts-builder, _bootstrap.nix, and stale _meta/ templates together.

Control-flow inversion

Hosts become composition roots; features become closures.

Granularity rule

Group by an operational concern, not mechanically by package. Keep Nook media or observability as cohesive directories when splitting them would make changes harder to understand. “Dendritic” does not mean “one tiny file per option.”

Representative shape

# core/module-classes.nix — one flake-parts module
{ inputs, ... }: {
  imports = [ inputs.flake-parts.flakeModules.modules ];
}

# features/access/ssh.nix — one aspect, several classes
{ inputs, ... }: {
  flake.modules.nixos.ssh = { ... }: { /* Linux SSH */ };
  flake.modules.darwin.ssh = { ... }: { /* macOS SSH */ };
  flake.modules.homeManager.ssh = { ... }: { /* user SSH */ };
}

# configurations/nook.nix — one explicit composition root
{ config, inputs, ... }: {
  flake.nixosConfigurations.nook = inputs.nixpkgs.lib.nixosSystem {
    modules = with config.flake.modules.nixos; [
      base-linux secrets ssh lisa nook-network nook-storage nook-services
    ];
  };
}

The outer flake-parts module captures inputs. Inner NixOS/Darwin/Home Manager modules should use normal module arguments such as config, lib, and pkgs; they no longer receive the whole flake through specialArgs.

Repository-specific map

Move by ownership, not with a flag-day rename.

overlays/ and _packages/ Feature-local packages with a minimal explicit override layer Prefer perSystem.packages and explicit module package options. Retain one ordered overlay composition only where global overrides are genuinely required. Never rely on module merge order for overlay ordering.

_meta/, _bootstrap.nix, builder input No long-term owner Move input declarations into aspects, cut over to import-tree, then delete together. nix run .#write-flake remains deterministic.

Execution sequence

Eight phases, each ending at a safe checkpoint.

PHASE 0
Baseline

Freeze the behavioral contract.

Create a migration branch and record the current flake outputs, selected option values, derivation paths, and known evaluation failures. Resolve the inaccessible Atlas input or explicitly record the authenticated environment needed to fetch it. Do not mix a service upgrade or input refresh into this migration.

Change

No configuration behavior. Add only reproducible inspection commands or notes if useful.

Gate

Nook evaluates; Vega and both home configurations are checked on a matching Darwin builder; Atlas has a trustworthy baseline.

Checkpoint

Before/after comparison inputs exist and the worktree has no unrelated changes.

PHASE 1
Spine

Introduce typed aspect namespaces without moving features.

Import inputs.flake-parts.flakeModules.modules once. Define the naming rules for nixos, darwin, and homeManager. Add short-lived compatibility aliases only where a converted aspect must still be consumed by an old constructor.

Change

Add the module-class foundation and one trivial pilot aspect, preferably SSH or XDG behavior.

Gate

New modules output lists the pilot in the correct class; importing it into the wrong class fails clearly.

Checkpoint

All existing host and home output names still evaluate unchanged.

PHASE 2
Reusable aspects

Convert the existing reusable module registries.

Migrate Agenix, sops-nix, auto-sync-update, Authentik, Matrix, AI skills, cli-proxy-api-plus, and XDG extra. Each feature file now publishes its own module class, declares its own flake input, and captures any input through the outer flake-parts module.

Change

Delete importApply and unused localFlake currying as each consumer moves.

Gate

Module option declarations and defaults compare equal; Matrix's private submodules remain one feature closure.

Checkpoint

The old NixOS and Home Manager registry files are empty and removable.

PHASE 3
Home Manager

Build one reusable Lisa home composition.

Convert common shell/editor/AI settings into Home Manager aspects and create two thin selections: lisa-nook and lisa-vega. Both standalone homeConfigurations and embedded Home Manager users consume those exact modules. Replace custom system arguments with pkgs.stdenv.hostPlatform.

Change

Remove directory-scanning imports and the custom flake.homeModules option.

Gate

Standalone and embedded home activation packages match for each host, aside from expected integration metadata.

Checkpoint

No Home Manager module receives inputs, system, or a home identifier through extraSpecialArgs.

PHASE 4
Linux canary

Decompose Nook into operational aspects.

Start with base access and packages, then network/DNS, storage, media, Home Assistant, caching/streaming, and observability. Nook is the useful local Linux canary because it also exercises embedded Home Manager. Keep the generated hardware module and nginx error-page function in ignored paths.

Change

Replace hosts/nook/default.nix's long import list with a named aspect selection.

Gate

Build the full Nook toplevel and diff its closure against Phase 0; investigate every service or package delta.

Checkpoint

Nook's output path and deploy-rs checks still resolve; nothing is activated.

PHASE 5
Darwin

Convert Vega and prove cross-platform composition.

Move remote builders, Nix/Lix, Homebrew, launchd, networking, fonts, packages, and local SSH access into Darwin or cross-class aspects. Evaluate and build this phase on Vega or with its configured aarch64-darwin builder; a Linux-only evaluator cannot validate all Home Manager sources used by Vega.

Change

Replace the Vega import root with explicit aspects and reuse the same lisa-vega home module.

Gate

Build darwinConfigurations.vega.system and the standalone Vega home activation package.

Checkpoint

Localhost SSH, deployment key wiring, remote builders, Homebrew taps, and activation behavior remain unchanged.

PHASE 6
Production services

Convert Atlas after its baseline is green.

Migrate base host policy, secrets, Matrix, Authentik, Forgejo, PostPlan, monitoring, and application services. Keep truly host-specific services host-specific; extract a shared aspect only when two hosts share policy, not merely because they use the same package.

Change

Replace unconditional module injection in the host factory with Atlas's explicit aspect selection.

Gate

Build the Atlas toplevel and both Atlas deploy-rs checks; compare services, users, ports, and secrets.

Checkpoint

No migration commit has reached main; Atlas's auto-update path cannot see a partial tree.

PHASE 7
Closure and cleanup

Localize packages, cut over the loader, and delete legacy glue.

Move package outputs and input declarations beside their consumers. Prefer explicit package options and perSystem.packages; keep a single ordered overlay composition for the few global overrides that cannot be removed safely. Audit every .nix file, move raw data/modules below an underscore-prefixed path, then switch to import-tree.

Change

Remove factories, registries, compatibility aliases, specialArgs, builder metadata, and dead template comments.

Gate

Regenerate flake.nix, run the file-semantics audit, and repeat all host/home/package/deploy builds.

Checkpoint

One loader, one module namespace, one source of input declarations, and no behavior changes hidden in cleanup.

Verification ladder

Prove wiring first, closures second, activation only later.

  1. Static semantics. Format check; every auto-loaded Nix file returns a flake-parts module; raw Nix values and generated hardware live only below ignored paths.
  2. Generated manifest. Run nix run .#write-flake and require a clean second run. Review the input diff; only the planned loader replacement should alter the lock graph.
  3. Output surface. Compare the names under NixOS, Darwin, Home Manager, packages, apps, overlays, deploy, and checks with the Phase 0 snapshot.
  4. Typed aspect surface. List the names under modules.nixos, modules.darwin, and modules.homeManager; ensure each host selects only its intended aspects.
  5. Targeted evaluation. Evaluate all five configurations and the deploy schema/activation checks. Do this on matching platforms where evaluation realizes platform-specific sources.
  6. Full builds. Build Nook, Atlas, Vega, both standalone Home Manager activations, published packages, and host-specific deploy-rs gates without activating anything.
  7. Closure review. Use nix store diff-closures (or equivalent recorded store paths) for each before/after system. Classify every difference as structural-only, expected loader metadata, or an unintended behavior change.
  8. Full-flake diagnostic. Run nix flake check --all-systems with matching builders. Existing generated-lock/devenv baseline failures may remain documented, but no new failure is accepted.

Suggested per-commit gate

Format → regenerate flake → evaluate every affected configuration → build its system/home closure → build the corresponding deploy checks. Run the complete matrix at the end of every host phase and again after loader cleanup.

Risk controls

Guard the boundaries most likely to drift.

RiskWhy it matters hereControl
Atlas baseline is not reproducible An unavailable locked source makes migration failures indistinguishable from existing failures. Restore authenticated fetch/evaluation or update that input in a separate, reviewed change before Phase 6.
Automatic server updates Nook and Atlas track main; a partial merge can become a deployment. Keep all phases on one branch/PR. Merge only the fully verified result. Actual rollout still requires explicit approval and follows the repository deployment policy.
Home Manager divergence Each Lisa home exists both standalone and embedded today. Make each pair consume the identical aggregate homeManager aspect; test both output paths.
Overlay order changes The default overlay composes package overrides in an explicit order, while module definitions do not promise overlay ordering. Move ordinary packages to perSystem; retain one explicit ordered composition for remaining global overrides.
Secret ownership drift Agenix and sops-nix span NixOS, Darwin, and Home Manager and carry activation-time paths. Move declarations without editing values; compare evaluated secret metadata before and after.
Hidden raw Nix files Several files return lists, attrsets, package functions, or ordinary NixOS/HM modules rather than flake-parts modules. Rename/move them below ignored underscore paths or wrap them before enabling import-tree for the full tree.
Over-abstraction Dendritic examples can tempt a rewrite into factories, constants modules, and tiny layers. Begin with simple aspects and lexical closures. Add a flake-level option only when two independently loaded aspects truly need a configurable shared value.

Definition of done

The migration is complete when these are all true.

All ordinary auto-loaded .nix files are flake-parts modules.
Raw modules, package functions, and data are visibly private under ignored underscore paths.
Features publish through flake.modules.nixos, .darwin, or .homeManager.
No central NixOS/Home Manager module registry or importApply wrapper remains.
No project-defined specialArgs or extraSpecialArgs are needed to pass inputs, system, host, or home identity.
Nook, Atlas, Vega, lisa@nook, and lisa@vega retain their exact flake output names.
Standalone and embedded Home Manager use the same selected Lisa aspects.
All flake inputs are declared by the feature or core concern that owns them.
flake.nix is still generated reproducibly by flake-file.
import-tree is the only tree loader; builder/bootstrap/template glue is gone.
All five configurations and their relevant deployment checks build on matching systems.
Before/after closure differences are reviewed and contain no unexplained behavior drift.
README and Justfile paths describe the new structure without changing deployment semantics.
No host has been activated or deployed merely by executing this migration plan.
