Forge / working plan

Adopt deploy-rs one host at a time

Add one locked deployment interface for Forge, remove the stale Altair output, keep Atlas owned by main, and make each remaining machine prove its SSH, activation, and recovery path before it joins the fleet.

Recommendation

Land the mechanism once, onboard hosts by readiness

Use a single flake-parts/deploy-rs.nix module for the deploy-rs input, deploy.nodes, the locked CLI app, and deploy checks. Remove Altair from the host outputs. Roll out Nook and Atlas first. Vega has a separate localhost-only deploy path and remains a manual workstation activation.

The final state has three managed hosts: Nook, Atlas, and Vega. Altair no longer exists, so retaining a buildable configuration for it would make Forge claim ownership of a machine that is gone.

Keep the first version small

  • One root-owned system profile per host.
  • No separate Home Manager profiles for Nook or Vega. Their system activations already include Home Manager.
  • No global remoteBuild setting. Let Vega use its existing builders.
  • GitHub Actions comes after the manual rollouts. It calls the same flake app for Nook and Atlas only, and promotes only a validated main commit.
  • No convenient deploy-all recipe. Automation names and gates each server; Vega remains outside the deployment workflow.

Implementation

Seven phases with a stop condition after each one

Phase 0

Set the operating rules

Record the deploy machine, source revision policy, and recovery method before adding an activator.

Work

  • Use Vega as the initial interactive deploy operator. Its SSH aliases, 1Password agent, and x86 Linux builder already exist.
  • Keep Atlas auto-sync enabled. Manual Atlas deploys must match a clean origin/main revision.
  • Require local console or provider console access for the first deploy-rs activation on each remaining host.
  • Keep private flake input credentials on the operator until phase 6 introduces a separate read-only automation credential for trusted post-merge jobs.

Stop condition

  • ssh -o BatchMode=yes nook true succeeds.
  • ssh -o BatchMode=yes atlas true succeeds.
  • sudo -n true succeeds through both SSH sessions.
  • A recovery route exists that does not depend on the same SSH configuration being changed.
Phase 1

Add the locked deploy-rs module

Put all deployment output construction in one flake-parts module. The generated root flake remains generated.

Work

  • Add deploy-rs through flake-file.inputs and make its nixpkgs input follow Forge.
  • Use the package, activators, and checks from that one pinned input. Do not mix the upstream library with an older nixpkgs CLI.
  • Delete the Altair block from darwinConfigurations and remove its host directory.
  • Define Nook and Atlas with sshUser = "lisa", profile user root, autoRollback = true, and magicRollback = true.
  • Use 600 seconds for activation and 60 seconds for confirmation. Leave remoteBuild and fastConnection at their defaults until measurement says otherwise.

Stop condition

  • The lock file pins the current upstream revision.
  • nix run .#deploy -- --version starts under Forge's pinned Lix.
  • The deploy output contains only Nook and Atlas at this point.
  • nix eval --json .#darwinConfigurations --apply builtins.attrNames returns only vega.
  • No credential, private key path, or raw private address appears in nix eval .#deploy --json.
Phase 2

Make checks cover what can be deployed

Deploy-rs checks validate the schema and the wrapped activation scripts. Ordinary host builds still catch host configuration failures.

Work

  • Merge deployChecks into the existing per-system checks without replacing the Nook and Vega build checks.
  • Add the missing Atlas build check. Vega's existing Darwin build check remains. Altair gets no check because its output is removed.
  • Build Nook and Atlas toplevels through Vega's existing x86 builder.
  • Keep the current unrelated full-flake failures visible. Use targeted acceptance checks until the generated-lock pruning, devenv, and import-from-derivation failures are handled separately.

Stop condition

  • The deploy schema check passes.
  • The activation wrapper check passes for every declared node.
  • Both Linux system closures build without deploying.
  • Running the flake generator a second time produces no diff.
Phase 3

Replace the stale operator commands

Expose a small command set that names one target. Leave installation and disk provisioning separate.

Work

  • Add Just recipes for dry activation, test activation, and normal activation of one named host.
  • Add a guarded Atlas recipe that refuses a dirty tree or a revision different from origin/main.
  • Remove or replace broken deployment recipes that reference old host names and absent flake apps.
  • Leave the destructive nixos-anywhere recipes outside this change. They install disks; deploy-rs switches an existing system.

Stop condition

  • Each recipe prints or targets exactly one deploy node.
  • No first-class recipe invokes a whole-fleet deployment.
  • The operator runbook states what --dry-activate, --test, and a normal switch change.
Phase 4

Onboard Vega deliberately

Deploy-rs has a native nix-darwin activator. Forge still needs a declared route into Vega before that helper is useful.

Work

  • Confirm Vega's stable self-target and host key handling.
  • Enable Apple's built-in OpenSSH server in Vega's host configuration, then bootstrap that setting once with the current local nix-darwin workflow.
  • Use deploy-rs interactive sudo for Darwin unless an existing non-interactive policy is already intentional. Do not add broad passwordless sudo just to avoid a prompt.
  • Use an explicit maintenance window because Vega is the daily-driver and its activation includes Home Manager and Homebrew cleanup.

Stop condition

  • BatchMode SSH works to Vega after the one-time bootstrap.
  • The sudo prompt works over SSH without storing a password.
  • The Darwin activator and host closure checks pass.
  • Vega can be targeted independently and is not pulled into a server deployment by accident.
  • No Altair configuration, output, check, or deploy node remains.
Phase 5

Roll out one platform canary at a time

A successful first activation seeds a deploy-rs-wrapped generation. Later rollbacks are safer than the first migration from a plain system generation.

Order

  1. Nook: dry activation, test activation, health checks, then switch.
  2. Atlas: merge first, confirm the auto-sync unit and its reboot timer are idle, pause the update timer, then repeat the same sequence. Leave that timer stopped if deploy-rs fails so it cannot retry the bad revision.
  3. Vega: Darwin rollout after phase 4, while Lisa is present and has a local recovery route.

Health checks

  • Reconnect with a new SSH session. Do not count the activation session itself.
  • Check failed system services and the host's critical workloads.
  • Confirm the active system generation matches the expected closure.
  • On Atlas, restart the auto-sync timer and confirm it sees the same main revision.
  • Wait through one normal operating interval before moving to the next critical host.
Phase 6

Promote the tested commands into GitHub Actions

Start this phase only after Nook and Atlas have each completed a manual deploy and rollback exercise. Keep the existing lock-update workflow separate. A new deployment workflow validates one immutable main commit and calls the same .#deploy app used by the operator. Vega is not an Actions deployment target.

Workflow and access

  • Use GitHub-hosted runners. Join the tailnet through Tailscale workload identity federation as a short-lived tagged node. Do not install a persistent Actions runner on Nook, Atlas, or Vega.
  • Give the tailnet tag access only to SSH on Nook and Atlas. Verify connectivity before loading the deployment key.
  • Create a dedicated SSH key and target-side deployment principal, plus a separate read-only credential for the private flake input. Do not export Lisa's personal key or 1Password agent into Actions.
  • Give the deployment principal only the non-interactive elevation needed by the deploy-rs activation wrapper. Do not add it to a broadly passwordless administrator group. Keep Lisa's account as the recovery path, not the CI identity.
  • Check in a deployment-only known_hosts file with the expected public host keys and require strict host-key checking.
  • Pin every third-party action to a full commit SHA. Default to contents: read; grant id-token: write only to jobs that join Tailscale.

Triggers and ordering

  • Pull requests run formatting and checks that do not need the private input. They receive no tailnet access, private-input credential, SSH key, or environment secret.
  • After a push to main, a trusted validation job obtains the read-only private-input credential and runs the complete evaluation, deploy checks, and target builds for that exact github.sha.
  • Only a successful validation may deploy that SHA to Nook. Nook's health gate then unlocks Atlas; either failure stops the chain.
  • No workflow event activates Vega. A suitable Darwin runner may evaluate or build its closure, but it must not receive a Vega SSH key, sudo path, or deployment environment.
  • Serialize the server pipeline with one concurrency group and cancellation disabled. A newer run must never terminate an activation already in progress.
  • Prove a compatible Linux builder for Nook and Atlas. Do not use --skip-checks to hide a platform mismatch.

Atlas changes deployment owner

Before push-to-main deployment is enabled for Atlas, merge the change that disables services.autoSyncUpdate and let the existing updater apply it once. Confirm its timer is gone. GitHub Actions then becomes the sole automatic deployment controller for Atlas.

Vega stays outside the automation boundary

Vega's deploy node uses localhost, interactive sudo, and a hostname guard. GitHub Actions may validate its Nix configuration, but no workflow may target .#vega for activation or hold credentials that could do so. Lisa remains present with local recovery access for every Vega switch.

Protection

  • Create separate GitHub environments for trusted validation, Nook, and Atlas so each job receives only the credentials it needs.
  • Restrict deployment environments to main. Require approval for Atlas where the repository's GitHub plan supports reviewers.
  • If protected-environment reviewers are unavailable, keep Atlas on explicit workflow_dispatch until an equivalent approval gate exists.
  • Do not use pull_request_target for deployment or check out untrusted pull-request code in a privileged job.

Stop condition

  • A pull request cannot access the tailnet, SSH keys, private input credential, or environment secrets.
  • The CI deployment principal cannot open an unrestricted root shell or use general administrator sudo.
  • The workflow records the commit SHA, target, activation result, and health-check result for every deployment.
  • A failed deploy or health check blocks every downstream host and leaves the previous system available through deploy-rs rollback.
  • Atlas has no active pull updater when its Actions deployment is enabled.
  • No deployment job targets .#vega, and Actions holds no credential or sudo path capable of activating it.

Safety

Rollback is useful, not magical

  • autoRollback reactivates the previous deploy-rs profile if activation fails.
  • magicRollback requires a fresh SSH confirmation after activation. Loss of connectivity triggers rollback.
  • The first deploy-rs activation is special because the prior generation may not contain deploy-rs's reactivation wrapper. Keep an independent console route.
  • Magic rollback cannot detect a problem that appears only after reboot.
  • An SSH address or port migration must use a separate two-step plan. Magic rollback intentionally rejects a change that prevents confirmation over the old route.
  • An Atlas rollback will not stay rolled back if main still contains the bad revision. Stop its updater or revert main before relying on a manual generation rollback.

Never attach Disko to a deploy profile

Nook and Atlas contain disk declarations used for installation and system configuration. The deploy-rs profile must wrap only config.system.build.toplevel. It must not run nixos-anywhere, Disko phases, formatting, or partition changes.

Acceptance

Definition of done for the manual rollout

  1. The generated flake pins deploy-rs through a flake-parts declaration, and the CLI and activation library come from that same input.
  2. Nook and Atlas have schema-checked NixOS system profiles using their verified SSH aliases, lisa login, and root activation.
  3. Altair's host directory, Darwin output, checks, and deployment references are gone.
  4. Vega has declared SSH, user, sudo, build-check, and recovery behavior before its Darwin profile is enabled.
  5. Nook and Atlas pass closure builds, dry activation, test activation, normal activation, fresh SSH reconnection, and host-specific health checks. Vega passes its closure build, manual localhost switch, and reconnection checks; deploy-rs dry and test modes are not used for nix-darwin.
  6. Atlas refuses off-main deployment and cannot race its auto-sync activation during the rollout.
  7. Nook and Vega still receive Home Manager only through their system activation. No duplicate profile owner exists.
  8. The repository has a tested manual rollback note for NixOS and nix-darwin, including the Atlas updater caveat.
  9. GitHub Actions deployment remains disabled until the Nook and Atlas rollouts have completed successfully. Vega remains manual regardless.

Scope correction

Altair leaves; Vega stays local

Altair is deletion work

Remove the stale host module and output in the same change that adds deploy-rs. Do not preserve it as an example, check, disabled node, or commented block. Git history already preserves the old configuration.
